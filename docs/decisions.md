# Decisions

Newest first. Each entry: what was decided, and what it changes in the build.

| Date | Decision | Effect |
| --- | --- | --- |
| 2026-11-25 | `conflicts` is a synced, server-created entity (adults read/resolve) | Conflict Inbox works offline from synced rows; revert = an ordinary newer update of the field, then mark resolved; protocol §6.1 |
| 2026-11-25 | Shared tablet: each PIN profile pushes with its own token; the tablet pulls with the account that set it up | The outbox records `member_id`/`device_id` per op; a profile first used offline keeps its ops queued until its token is fetched; what each profile may see on the tablet is limited in the app by role |
| 2026-11-25 | Members' `pin_hash` is bcrypt `$2y$` cost 10, written by the app | Same hash checked offline on the tablet and by Laravel `Hash::check` on `/auth/pin`; ~80 ms per check |
| 2026-11-25 | App database: SQLite3MultipleCiphers (`sqlite3` hook `source: sqlite3mc`) instead of `sqlcipher_flutter_libs` (end-of-life) | Android database encrypted with `PRAGMA key` (key in secure storage); the same engine has a WASM build, so web encryption can be added later without changing engines; web database is unencrypted for now (vault fields are encrypted on their own) |
| 2026-11-25 | Add Debts & Loans module (loans, credit cards, prenda tickets, money lent) and a Subscriptions tab in Bills | 14 modules; payments are append-only and post to the expense ledger; prenda ticket photos go to the Vault; Debts & Loans ships in Phase 2, Subscriptions in Phase 1 |
| 2026-11-25 | Web app on Cloudflare Pages, API on Hostinger (`app.` and `api.` subdomains) | CORS limited to the Pages origin; Sanctum bearer tokens (no cookies); GitHub Actions builds Flutter web and runs `wrangler pages deploy`; `_headers` (COOP/COEP) and `_redirects` in `app/web/` |
| 2026-11-25 | Shared household tablet with PIN profiles for kids and helpers | Built in Phase 0 with auth and roles |
| 2026-11-25 | UI language: English for now | Strings still go through Flutter localization (ARB) files so Filipino can be added later |
| 2026-11-25 | App name: HomeSync | Package id `com.johncris09.homesync` |
| 2026-11-25 | One repo (`app/`, `api/`, `docs/`) | Protocol changes land in app and API in the same pull request |
| 2026-11-25 | Platforms: Android and web (Flutter for both); no iOS for now | Flutter project created with `--platforms=android,web`; web uses Drift on SQLite WASM (OPFS) |
| 2026-11-25 | Hosting: Hostinger shared hosting only; background jobs via cron | One cron entry runs `schedule:run` every minute; database queue drained with `queue:work --stop-when-empty`; no websockets |
| 2026-11-25 | Document vault: strong end-to-end encryption | AES-256-GCM on device; server stores ciphertext only; owner recovery code; on web the key is derived from a vault passphrase each session |
| 2026-11-25 | Audience: this household only | No public sign-up, subscriptions or store listing; owner invites members |
| 2026-11-25 | Offline-first with outbox + push/pull sync, HLC-based conflict rules | See `sync-protocol.md` |
| 2026-11-26 | Members are managed by the owner in the app; the owner role is not assignable there | Household members screen (owner only, matches `members.write = ['owner']`): add/edit name, role (adult/teen/child/helper/viewer), colour as `#RRGGBB`; set/change/remove tablet PIN (entered twice); remove = soft delete; the owner can't remove themself or change their own role |
| 2026-11-26 | App bootstraps from a snapshot when its cursor is 0 | Found in the first real-hub test: rows the hub writes itself (owner from `homesync:setup`) are not in the change log, so pull alone never delivered them. Cheap while the log is empty; normal pulls after |
| 2026-11-26 | The person who sets up the shared tablet always has a way back to their profile | Found in the real-hub test (tablet got stuck on a helper). After tablet sign-in they must choose a tablet PIN (shown only while they are active); its bcrypt hash is kept on the tablet (works for any role, offline, before members sync) and, for the owner, also written to their `pin_hash` so it syncs. Switching to them accepts either |
| 2026-11-26 | Phase 1 starts with Pantry & Grocery | Its tables already existed on both sides and it is used daily by every role (helpers included); the other Phase 1 modules need new tables first |
| 2026-11-26 | Pantry & Grocery behaviour | Stock-take sends the difference as an increment so concurrent use elsewhere is kept; "running low" only when a minimum is set; "expires soon" = within 7 days, expired shown in Gumamela; "clear bought" tombstones bought items; adding a pantry item to the list skips names already on it; viewers read only |
| 2026-11-26 | Budget before Bills | Bill payments post to the expense ledger, which Budget introduces |
| 2026-11-26 | Budget model | Fixed spending categories for Phase 1 (food, utilities, transport, school, health, household, load & internet, personal, giving, other) stored as keys; one monthly limit per category, same every month; ledger amounts signed (expenses negative, income positive) in centavos; fix a wrong entry by removing and re-adding (append-only) |
| 2026-11-26 | Derived ids for one-row-per-key entities (protocol §2.1) | `budgets` id = UUIDv5(namespace, `budgets/<household>/<category>`), so offline creates on two devices merge into one row; the hub applies an insert onto an existing row with base version 0 so an overwritten reviewed value always reaches the Conflict Inbox |
| 2026-11-26 | Bills model | A bill row is one due date (the existing `bills` table); monthly bills share `series_id` and paying one adds next month's with a derived id (`<series_id>/<due_on>`), keeping the series' day of month (31st → Feb 28 → Mar 31). Paying asks for the actual amount (the stored amount is a guess for variable bills). Subscriptions are their own table (price, monthly/yearly, next due date); paying moves the date one cycle on. Both adults only |
| 2026-11-26 | No `bill_payments` table | The ledger entry is the payment record (`source_type` `bill`/`subscription`, `source_id`); a separate table would duplicate it. Revisit if partial payments are needed |
| 2026-11-26 | A payment made on two devices is recorded once | Payment ledger entries use derived ids (`bill/<bill_id>`, `subscription/<id>/<due_on>`); the hub answers an insert onto an existing append-only record with `merged` and keeps the first. Undo is for the person who marked it paid (forward-only rule) and removes the entry; paying again uses a random id |
| 2026-11-26 | Bills header turns Gumamela only while something is overdue | Narra otherwise; Gumamela is reserved for overdue/emergencies |
| 2026-11-26 | Chores next after Bills | Used daily by everyone (kids and helpers included); Calendar is the last Phase 1 module |
| 2026-11-26 | Chores model | `chores` = daily, weekly on one weekday, or once on a date, assigned to a member or anyone; adults manage them. Doing one appends a `chore_completions` row (chore, member, local date); "done today" = a completion today. No `chores.is_done` flag (dropped from the forward-only list): two people doing it offline both keep credit, and daily chores reset by date. Undo deletes your own completion. Kids, teens and helpers tick their own and unassigned chores; adults tick any; viewers read only. Overdue once-chores stay on Today in Gumamela |
| 2026-11-26 | Calendar model | One `events` row per event: first date, optional local start/end time (`HH:MM`, null = all day), repeat `none`/`weekly`/`monthly`/`yearly` (yearly covers birthdays; Feb 29 falls on Feb 28 in other years), who it is for (a member or everyone), place and note. Dates of repeats are computed on the device, not stored. No per-date exceptions or end date yet: editing a repeating event changes every date. Everyone but viewers adds events; adults change any, others only the ones they added (`created_by`, checked in the app) |
| 2026-11-26 | Bills on the calendar | Adults see unpaid bills and each subscription's next due date on the calendar (Mangga dots), read from the Bills tables, not copied into `events` |
| 2026-11-26 | Who sees money | Adults see the ledger and budgets; teens, children and helpers can record expenses and see only their own entries (also on the shared tablet, where the ledger is pulled with an adult's token); viewers don't get the Budget module |
| 2026-11-26 | Deploys from GitHub Actions on push to `main` | Hub: tests, `composer install --no-dev` on the runner, rsync over SSH to Hostinger (keeping `.env` and `storage/`), then `migrate --force` + `optimize` behind maintenance mode; no git or composer needed on the server. Web: tests, `flutter build web` with `API_BASE_URL`, `wrangler pages deploy`. Both use the GitHub environment `production`; secrets live only there. CI runs tests on PRs and `develop`. CORS allows only `CORS_ALLOWED_ORIGINS` (none by default in production). Steps in `docs/deploy.md` |
| 2026-11-26 | Android release signing key | Release APKs are signed with one upload key kept outside the repo (`android/key.properties` points to it; both ignored by git). Android only installs an update signed with the same key, and reinstalling wipes data that has not synced yet, so the key and its password are backed up off this PC. Without `key.properties` the build falls back to the debug key, for local tries only |
| 2026-11-26 | One version per release, from a tag | Replaces deploying on every push to `main`. Pushing a tag `vMAJOR.MINOR.PATCH` on `main` runs `release.yml`: the hub deploys first, then (only if it succeeded) the web app and a signed APK, which is published as a GitHub Release; the family installs from there (no Play Store). All three carry the tag's version: `APP_VERSION` dart-define in the app, `api/VERSION` on the hub (sent as `X-HomeSync-Version`), Android versionCode `MAJOR*10000 + MINOR*100 + PATCH` so it always grows with no file change. Home shows "Version x · hub y". The sync protocol number stays separate and only tracks compatibility. The signing key reaches the runner as base64 secrets and is deleted after the build. No Windows app: on a PC, install the web app from the browser |
| 2026-11-26 | Phase 2 starts with Debts & Loans | It builds on the ledger and the payment pattern from Bills; the Vault needs its key handling first |
| 2026-11-26 | Debts model: one `debts` table, payments in append-only `debt_payments` | Replaces the draft's separate loans, credit cards, pawn tickets and receivables tables (and their payment tables). `kind` is `loan`, `card`, `pawn` or `lent`; labels in the app follow it. The balance is not stored: principal plus `charge` rows minus `payment` rows (`interest` rows are paid but leave it alone, e.g. renewing a pawn ticket), so payments recorded on two devices offline both count. Unlike Bills, a payments table is needed because charges and money paid back on a loan you gave are not cash spending, so they cannot live in the ledger. Adults only |
| 2026-11-26 | Debt payments in the ledger | A payment or interest on a loan, card or pawn ticket posts an expense under a new Budget category **Debt payments** (`debt`), id derived from the payment so removing the payment removes it. Money lent and paid back is not posted (it is the household's own money returning) |
| 2026-11-26 | Debt due dates and closing | A monthly debt's due date (a pawn ticket's maturity) moves one month on when a payment or interest is recorded within 7 days of it or after; earlier payments leave it. A payment that brings the balance to zero closes the debt (paid off, redeemed, repaid); closing is forward-only and only the person who closed it can reopen it (`closed_by`). Only the person who recorded a payment can remove it. Overdue money lent does not turn the header Gumamela |
| 2026-11-27 | App logo: a roof over sync arrows | Replaces the default Flutter icon. A Narra roof over Dahon sync arrows and a Dahon floor line on Capiz, with no yellow: the home that keeps itself in step. The source is `app/branding/logo.svg`; `python branding/render.py` (from `app/`, needs Chrome or Edge and Pillow) renders the web favicon, PWA icons (normal and maskable), the Apple touch icon and the older Android launcher PNGs. On Android 8 and newer, the adaptive icon is a vector drawable (`ic_launcher_foreground.xml`, also used as the themed monochrome icon) on a Capiz background, so edit it together with the SVG. The installed app is now named "HomeSync" on Android and web |
| 2026-11-27 | Grocery history: clear keeps items, dated by when they were bought | Chosen from mockups by the owner: ticking an item records today, and a date chip on the bought item (or the edit sheet) moves it to another day; no extra tap in the usual case. The date is the date bought, not a planned shopping date. "Clear bought" now sets a new `cleared_at` instead of deleting (replaces "clear bought tombstones" from 2026-11-26, since tombstones are pruned after 90 days), so a separate Past groceries screen (button under the list) can show everything bought, grouped by day, newest first; an item can be put back on the list from there (name, quantity, store; skipped if already listed). Items cleared before this change were deleted and do not appear. Removing an item is still a delete. Viewers can look but not add back |
| 2026-11-27 | Grocery planned shopping day | The owner clarified that the date they need is the day they plan to buy an item, often in the future, so it can be set while the item is still on the list. New nullable `planned_on` date on `grocery_items`. A date chip in the add field sets the day for the items typed next; each item has a chip to set, change or remove its day; the edit sheet has the same field. The list groups by day, soonest first, "No date" last (no headings when nothing has a date); a day already past shows in Gumamela; the header caption shows the next shopping day from today on. The date bought and Past groceries stay as they are. Items added back from Past groceries or from the pantry get no date |
